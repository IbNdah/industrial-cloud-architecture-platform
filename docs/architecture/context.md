# Industrial Cloud Architecture Platform — Project Context

**Document status:** Draft — S1 Architecture Definition
**Version:** 0.1.0
**Scope:** Industrial Asset Monitoring & Predictive Maintenance
**Cloud platform:** Microsoft Azure

## 1. Purpose

The Industrial Cloud Architecture Platform demonstrates how to design a secure, resilient, and scalable cloud architecture for industrial monitoring and predictive maintenance.

The project builds on two existing foundations:

- **Azure Enterprise Cloud Foundation:** reusable cloud governance, security, networking, and operational capabilities.
- **EV Fleet Monitoring Platform:** reusable IoT ingestion, telemetry processing, monitoring, API, and visualization patterns.

The objective is to extend these capabilities to an industrial OT environment without rebuilding existing components unnecessarily.

## 2. Business Problem

Industrial production depends on the availability of critical assets such as electric motors, pumps, conveyors, and fans.

Unexpected equipment failures can lead to:

- Unplanned production downtime.
- Increased maintenance costs.
- Reduced equipment availability.
- Limited visibility into equipment health.

The proposed solution collects equipment telemetry, evaluates operational conditions, identifies rule-based anomalies, and makes asset health information available to maintenance and operations teams.

The initial implementation demonstrates condition monitoring and threshold-based anomaly detection. It does not claim to implement or validate a production-grade predictive maintenance model.

## 3. Project Objectives

The project aims to:

1. Define a reference architecture connecting industrial OT systems to Microsoft Azure.
2. Demonstrate secure telemetry ingestion from an industrial Edge Gateway.
3. Preserve local industrial control and operations during cloud outages.
4. Implement persistent local buffering and telemetry replay.
5. Process telemetry and detect anomalies using configurable rules.
6. Store industrial asset, telemetry, and alarm information in PostgreSQL.
7. Expose monitoring information through a DashboardService API and Grafana.
8. Apply infrastructure as code, automated validation, and observability practices.
9. Produce a reusable architecture pattern for manufacturing, energy, and other industrial environments.

## 4. Scope

### 4.1 In scope

- Simulated industrial assets and telemetry.
- Simulated OPC UA server for the initial implementation.
- Industrial Edge Gateway packaged with Docker.
- OPC UA data acquisition and telemetry normalization.
- Local persistent buffering using SQLite.
- MQTT over TLS between Edge and cloud ingestion.
- Azure IoT Hub.
- Azure Functions for telemetry processing and API endpoints.
- Azure Database for PostgreSQL Flexible Server.
- Rule-based anomaly detection and asset health assessment.
- Grafana dashboards.
- Terraform-based infrastructure deployment.
- CI/CD and automated quality checks.
- Security, network segmentation, monitoring, and operational documentation.

### 4.2 Out of scope for the initial implementation

- Direct cloud control of PLCs or industrial actuators.
- Production deployment against real industrial equipment.
- Machine-learning-based failure prediction.
- Kubernetes or AKS.
- Kafka or a separate Event Hubs namespace without a demonstrated requirement.
- A dedicated data lake or separate time-series database.
- A full Azure Digital Twins implementation.
- High-availability industrial edge clustering.
- Certification or formal compliance validation for a production OT environment.

These capabilities may be reconsidered if justified by explicit requirements.

## 5. Industrial Use Case

The initial environment represents one industrial site with five monitored assets:

| Asset ID | Asset type | Criticality | Initial telemetry |
|---|---|---|---|
| M-101 | Electric motor | High | Temperature, vibration, current, RPM |
| M-102 | Electric motor | High | Temperature, vibration, current, RPM |
| P-101 | Pump | High | Pressure, temperature, vibration, flow |
| C-101 | Conveyor | Medium | Speed, current, vibration |
| F-101 | Fan | Medium | RPM, temperature, vibration |

Telemetry is generated by simulated equipment and made available through an OPC UA server. The Edge Gateway acquires and validates the data before forwarding it to Azure.

The cloud processes telemetry, identifies threshold violations, persists records, and exposes the resulting information through dashboards.

## 6. Architectural Principles

### 6.1 OT autonomy

Industrial control remains local. PLCs and SCADA/HMI systems must continue operating if Azure connectivity is lost.

### 6.2 No direct cloud-to-PLC control path

The initial architecture supports telemetry acquisition and monitoring. It does not introduce a direct Azure-to-PLC control channel.

### 6.3 Secure-by-design connectivity

OT, Industrial DMZ, and cloud environments are separated by explicit network boundaries and restricted communication flows. Edge-to-cloud communication uses TLS and an identifiable, revocable device identity.

### 6.4 Resilience at the Edge

The Edge Gateway validates and normalizes telemetry, buffers messages persistently during connectivity outages, and replays queued messages after reconnection.

### 6.5 Reuse before introducing new services

Existing components and patterns from the Azure Enterprise Cloud Foundation and EV Fleet Monitoring Platform should be reused when they meet the industrial requirements.

### 6.6 Simplicity and incremental evolution

The initial architecture uses Azure IoT Hub, Azure Functions, PostgreSQL, SQLite, Docker, Terraform, and Grafana. Additional platforms are introduced only when measurable requirements justify them.

### 6.7 Observable operations

Telemetry processing, Edge connectivity, queue status, errors, and application health should be observable through appropriate logs, metrics, and alerts.

## 8. Relationship to Existing Projects

### Azure Enterprise Cloud Foundation

Provides the baseline for cloud governance, identity, network design, security controls, monitoring, and infrastructure management. The industrial workload should consume relevant foundation capabilities rather than recreate them.

### EV Fleet Monitoring Platform

Provides reusable implementation patterns for telemetry simulation, MQTT integration, Azure IoT Hub, Azure Functions, infrastructure as code, observability, and Grafana integration.

The industrial project introduces new requirements for OPC UA acquisition, OT network segmentation, persistent Edge buffering, industrial asset modeling, and PostgreSQL-based persistence.

## 9. Success Criteria

The initial project is considered successful when:

- Industrial telemetry can be acquired from the simulated OPC UA source.
- The Edge Gateway validates and normalizes messages.
- Messages are buffered persistently during a simulated cloud outage.
- Queued messages are replayed after connectivity is restored.
- Azure receives and processes telemetry securely.
- Threshold violations produce identifiable alarms.
- Asset and telemetry information is persisted in PostgreSQL.
- Grafana displays asset status, telemetry trends, and alarms through the DashboardService API.
- Infrastructure and application quality checks are automated.
- Architecture decisions, limitations, and operational procedures are documented.

## 10. Constraints and Assumptions

- The first implementation is a demonstrator, not a production-certified industrial solution.
- Industrial assets and the OPC UA source are simulated.
- Azure services are selected according to the initial workload and cost constraints.
- PostgreSQL connectivity should be private where supported by the deployment design.
- Authentication, network integration, and service-specific Terraform capabilities must be validated during implementation.
- Rule-based anomaly detection is the initial baseline; predictive machine learning is deferred.
